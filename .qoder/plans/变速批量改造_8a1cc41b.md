# 变速功能批量改造计划

## 摘要

当前变速功能仅支持单一片段加速且输出不完整。改造为：支持多片段批量变速 + 合并回完整视频。采用**主进程原子操作**方案（参照 `batchAdjustColor` 范式）：新增 `batchSpeedMerge` 编排函数，单次加锁、for-await 串行调用 `changeSpeed`（变速段重编码）+ `splitVideo`（未变速段流拷贝）+ `mergeVideos`（合并），全程统一进度聚合与临时文件清理。前端抽 `useSpeedBatch` composable 管理片段列表，SpeedPanel 改造为双模式面板。

## 核心约束（已验证）

| 约束 | 文件:行号 | 影响 |
|------|----------|------|
| 全局单锁，占用时直接抛 `LockTimeoutError`，默认 30s 超时 | `lock.ts:7-43` | 批量必须单次加锁，不能前端串行调多次 IPC |
| `currentProc` 全局单槽，`setFfmpegProc` 直接覆盖 | `ffmpeg-shared.ts:151,183-185` | 子进程必须顺序执行，不能并发 |
| `changeSpeed` 入口调 `resetCancelled()` | `ffmpeg-speed.ts:73` | 编排器循环顶部 `isCancelled` 检查仍有效（取消后子函数 close 回调 resolve(false)，下一轮 break） |
| `changeSpeed` speed=1.0 走 `-c copy` 流拷贝 | `ffmpeg-speed.ts:76-85` | 未变速段若用 changeSpeed(speed=1) 保留原编码，与非 h264 源的变速段(h264)不一致 → merge `-c copy` 失败 |
| `mergeVideos` 用 concat demuxer + `-c copy` | `ffmpeg.ts:201-208` | 要求各段编码一致 |
| `batchAdjustColor` for-await + isCancelled 短路 + currentFile 映射 | `ffmpeg-color.ts:166-200` | 批量编排的已验证范式 |
| `wrapOperation` 支持 `timeoutMs` 第 5 参 | `index.ts:124-141` | 长视频批量重编码需调长超时（参照 batchConvertFormat 600000） |
| `ProgressInfo` 已有 `currentFileName?` 字段 | `preload/index.ts:10` | 批量进度文字"变速 2/5"可直接用 |
| `useCompressBatch` 模块级状态 + runId 防竞态 | `useCompressBatch.ts:19-35` | composable 范式参考 |

## 实施步骤

### 步骤 1：新增 SpeedSegment 类型
- 文件：`src/renderer/src/types/file.ts`（ClipItem 后新增）
- 不复用 ClipItem（变速段无需 sourceFile/selected，语义不同）
```ts
/** 变速片段：用户在时间轴上标记的待变速区间 */
export interface SpeedSegment {
  id: string
  startSec: number
  endSec: number
  duration: number
  speed: number
}
```

### 步骤 2：changeSpeed 增加 forceReencode 参数（解决编码一致性）
- 文件：`src/main/modules/ffmpeg-speed.ts`
- `SpeedChangeOptions` 接口（L20-30）增加 `forceReencode?: boolean`
- L76 `isUnitySpeed` 判断改为：`const isUnitySpeed = Math.abs(opts.speed - 1.0) < 0.001 && !opts.forceReencode`
- 效果：`forceReencode=true` 时即使 speed=1 也走重编码分支（libx264 CRF18），保证与非 h264 源的变速段编码统一
- **同步 preload**：`index.ts` L103 和 `index.d.ts` L100 的 `changeSpeed` opts 类型增加 `forceReencode?: boolean`

### 步骤 3：主进程实现 batchSpeedMerge 编排函数
- 文件：`src/main/modules/ffmpeg-speed.ts`（changeSpeed 之后新增）
- 签名：
```ts
interface BatchSpeedOptions {
  input: string
  output: string
  segments: SpeedSegment[]  // 已按 startSec 排序
  sourceDuration: number   // 源视频总时长
  sourceCodec?: string     // 源视频编码（前端从 videoMeta.codec 传入）
  onProgress?: ProgressCallback
}
export async function batchSpeedMerge(opts: BatchSpeedOptions): Promise<boolean>
```
- 逻辑（参照 `batchAdjustColor` L166-200 范式）：
  1. `resetCancelled()` 一次
  2. 按 segments 边界计算未变速间隙：`[0, seg0.startSec]`、`[seg0.endSec, seg1.startSec]`、...、`[segN.endSec, sourceDuration]`；过滤掉 duration≤0 的空间隙
  3. 构建有序任务列表：变速段标记 `type:'speed'`，未变速段标记 `type:'copy'`
  4. `totalSteps = tasks.length + 1`（+1 为 merge）；维护 `tempFiles: string[]` 和 `step=0`
  5. `getTempDir()` 取临时目录
  6. for-await 遍历 tasks：
     - 循环顶部 `if (isCancelled) break`
     - 变速段：`await changeSpeed({input, output:tempFile, startTime:seg.startSec, duration:seg.duration, speed:seg.speed, onProgress: remap(step, totalSteps, '变速')})`
     - 未变速段：若 `sourceCodec` 以 `h264` 开头 → `await splitVideo({input, output:tempFile, startTime:secondsToTimecode(start), duration:secondsToTimecode(dur), onProgress: remap(step, totalSteps, '截取')})`（快路径）；否则 → `await changeSpeed({input, output:tempFile, startTime:start, duration:dur, speed:1, forceReencode:true, onProgress: remap(step, totalSteps, '截取')})`（重编码保证一致性）
     - 成功后 `tempFiles.push(tempFile)`；`step++`
     - 子调用失败（reject）：break，跳到 finally 清理
  7. `if (isCancelled) break`（merge 前再检查）
  8. `await mergeVideos({inputs: tempFiles, output: opts.output, onProgress: remap(step, totalSteps, '合并')})`
  9. **进度映射函数 `remap`**（参照 `batchAdjustColor` L180-188）：
     ```ts
     function remap(step: number, total: number, label: string): ProgressCallback {
       return (data) => opts.onProgress?.({
         ...data,
         currentFile: step + 1,
         totalFiles: total,
         currentFileName: `${label} ${step + 1}/${total}`
       })
     }
     ```
  10. **finally**：`Promise.allSettled(tempFiles.map(f => deleteFile(f)))` 清理所有临时片段（成功合并后清理、失败/取消也清理）
- 注意：`splitVideo` 的 startTime/duration 是 string timecode，需用 `secondsToTimecode`（`utils/time.ts` 已有，但主进程没有该函数——主进程直接用 `String(seconds)` 即可，ffmpeg `-ss`/`-t` 接受秒数）
- import：`splitVideo` from `./ffmpeg`、`SpeedSegment` 类型（主进程需定义或从渲染进程类型导入——主进程独立定义 `SpeedSegment` 接口避免跨进程依赖）

### 步骤 6：新建 useSpeedBatch composable
- 文件：`src/renderer/src/composables/useSpeedBatch.ts`（新建，参照 `useCompressBatch.ts` 结构）
- 模块级状态（跨页面持久，参照 `useCompressBatch.ts:19-35`）：
  - `speedSegments = ref<SpeedSegment[]>([])`
  - `errorMsg = ref('')`
  - `let runId = 0`
- 导出函数 `useSpeedBatch(opts)` 返回：
  - `speedSegments` / `errorMsg`
  - `addSegment(trimStart: number, trimEnd: number, speed: number)`：生成 id（`speed_${Date.now()}_${counter}`），push 后按 startSec 排序
  - `removeSegment(id: string)`
  - `updateSegmentSpeed(id: string, speed: number)`
  - `clearSegments()`
  - `canBatch = computed(() => speedSegments.value.length > 0 && !store.isProcessing)`
  - `startBatchSpeed(input: string, outputDir: string, sourceDuration: number, sourceCodec: string)`：
    1. `const thisRunId = ++runId`
    2. `store.start('speed')`
    3. `await window.electronAPI.batchSpeedMerge({input, output: outputDir, segments: speedSegments.value, sourceDuration, sourceCodec})`
    4. 成功 → `store.finish()` + `clearSegments()`
    5. 失败/取消 → `errorMsg.value = ...` + `store.reset()`
    6. `if (thisRunId !== runId) return`（防竞态）
  - `startSingle(input, output, startTime, duration, speed)`：保留单段快捷路径，直接调 `changeSpeed`（不 forceReencode，走流拷贝快路径）
- 进度：由 `SplitMergeView.onMounted` 注册的 `onProgress` → `store.update(info)` 统一处理（currentFile/totalFiles/currentFileName 已由主进程聚合）

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| **30s 锁超时误释放**（长视频批量重编码） | `lock.ts:13` 默认 30s，批量必超 → 锁释放 → 用户可发新操作 → resetCancelled 互相覆盖 | `wrapOperation` 显式传 `600000`（10min），对齐 batchConvertFormat/tts 先例 |
| **ffmpeg 进程风暴**（若误并发） | 全局单槽 currentProc 被覆盖，取消/进度全乱 | 强制 for-await 顺序（参照 batchAdjustColor L172），重编码 CPU-bound 并发只 thrash |
| **临时文件残留**（崩溃/取消） | N 个 temp 段泄漏 | batchSpeedMerge finally 集中 `Promise.allSettled(deleteFile)`；兜底 index.ts window-all-closed 已 rmSync 整个 sn-video-clips 目录 |
| **取消竞态**（子函数各自 resetCancelled） | cancel 标志被子函数入口清掉 | 编排器循环顶部 `if(isCancelled) break`（batchAdjustColor L173 同款），不依赖子函数传播；cancel 经 currentProc kill 当前进程 |
| **merge 阶段编码不一致**（非 h264 源） | 变速段 libx264 + 未变速段原编码 → concat -c copy 失败 | sourceCodec 检测：h264 源走 splitVideo -c copy（快），非 h264 源走 changeSpeed forceReencode=true（重编码统一 h264） |
| **段重叠/乱序** | 临时文件错乱、合并时间错位 | addSegment 时按 startSec 排序插入；UI 添加前可选校验与已有段无重叠 |
| **大文件耗时** | 多段重编码累计时间长 | 进度 currentFileName='变速 2/5' 让用户有预期；ProgressPanel cancel 按钮可用 |
| **onProgress 监听器** | speed 模式复用 SplitMergeView.onMounted 的全局监听器，无需 SpeedPanel 自行注册 | 当前架构正确（SpeedPanel 作为子组件，父组件仍挂载），保持不变 |
| **useTrimTimeline 仅单区间** | 改其内部会波及 split 模式 | 不改 composable；用"单段时间轴 + 段列表 + 添加按钮"模式，与裁剪模式交互一致，零波及 split |

## 被拒绝的替代方案

1. **前端编排（渲染进程串行调 changeSpeed+splitVideo+mergeVideos）**（Agent C 方案）：虽改动行数最少，但全局单锁非排队而是直接抛错（lock.ts:30-32），每次 IPC 调用经 wrapOperation 会 acquireLock/releaseLock，段间锁释放窗口允许用户插入新操作；每个子函数入口 resetCancelled() 会清取消标志；进度映射需前端 onProgress 重注册（preload onProgress 内部 removeAllListeners 会覆盖），脆弱。**正确性不可接受**。

2. **merge 失败时 fallback 重编码合并**（Agent B 提及）：需在 mergeVideos 内部增加编码检测和 fallback 逻辑，改动 mergeVideos 影响所有合并场景（split/merge 模式），回归面过大。改为在 batchSpeedMerge 编排层通过 sourceCodec 预判，未变速段提前选择流拷贝或重编码，更精准。

3. **新增 SpeedSegment 复用 ClipItem**：ClipItem 含 sourceFile/sourceFileName/selected/outputFile 等字段，变速段无需这些（统一源、全部处理、主进程管临时文件）。复用会导致语义混淆和冗余字段，故新增独立类型。

4. **时间轴改多区段（改 useTrimTimeline）**：useTrimTimeline 仅支持单 trim 区间，改其内部会波及 split/audio 模式。用"单段时间轴 + 添加按钮累积段列表 + 浮层叠加渲染"模式，与裁剪模式交互一致，零波及其他模式。
